# Emacs

[`QDtb/GNU Emacs/`](https://github.com/natebass/QDtb/tree/master/GNU%20Emacs)
is an Emacs 31 configuration. It is smaller than the Neovim side by a long way
— one `init.el` and seven library files — and it is still being cleaned up, so
this page covers the part that is settled: the structure.

Emacs is not a side project here. It is the editor `$EDITOR` points at:
[`fish/conf.d/10-env.fish`](/docs/fish/startup#10-envfish--the-environment)
sets `EDITOR` to `emacsclient -t` and `VISUAL` to `emacsclient -c -a emacs`,
so anything that opens an editor opens this.

## `init.el`

Four blocks, in order.

### Packages and `custom.el`

```elisp
(require 'package)
(add-to-list 'package-archives '("melpa" . "https://melpa.org/packages/") t)
(package-initialize)
(setq custom-file (expand-file-name "custom.el" user-emacs-directory))
(load custom-file t)
```

The built-in package manager, with [MELPA](/docs/other/emacs-melpa) added.

`custom-file` is the important line. By default, Emacs's Customize interface
writes into `init.el` itself — so a setting you changed through a menu lands
in the middle of your hand-written configuration, and the two fight the first
time you edit either. Pointing `custom-file` at its own file keeps them apart.
The `t` on `load` means "do not complain if it is not there yet".

`custom.el` is [in `.gitignore`](#what-is-not-committed): it is machine state,
written by Emacs, not configuration you wrote.

### `user-lisp`

```elisp
(add-to-list 'load-path (expand-file-name "user-lisp" user-emacs-directory))

(require 'my-editing)
(require 'my-project)
(require 'my-treesit)
(require 'my-test)
```

See [below](#user-lisp).

### Atomic Chrome

```elisp
(require 'atomic-chrome)
(atomic-chrome-start-server)
```

The one external package. It runs a WebSocket server that lets a browser
extension hand a textarea to Emacs for editing — so a long comment or a
Markdown box in a browser is edited here instead of in a `<textarea>`.

It is the only entry in `package-selected-packages`, and it brings
`websocket` with it.

### Terminal integration

```elisp
(defun my/set-ghostty-title ()
  "Update Ghostty window title to show current buffer and relative path."
  (unless (display-graphic-p)
    …
    (send-string-to-terminal (format "\e]2;%s - Emacs\a" …))))

(add-hook 'buffer-list-update-hook #'my/set-ghostty-title)

(xterm-mouse-mode 1)
(when (fboundp 'pixel-scroll-precision-mode)
  (pixel-scroll-precision-mode 1))
```

Three things for running in a terminal:

- **The window title.** `\e]2;…\a` is the OSC escape sequence terminals read
  as "set the window title". `(unless (display-graphic-p) …)` skips it in a
  GUI frame, where Emacs sets the title itself. This is the same job Neovim's
  [`window_title.lua`](/docs/neovim/custom#the-rest-of-luapluginsqdtb) does
  through `xdotool`.
- **`xterm-mouse-mode`** — the mouse works in a terminal frame.
- **`pixel-scroll-precision-mode`**, guarded with `fboundp` so it is a no-op on
  an Emacs too old to have it.

`buffer-list-update-hook` fires often, which is what keeps the title current
— and is also worth knowing if the title ever needs to do more work than a
`format` and a write.

## `user-lisp`

Seven files, one subject each, all `lexical-binding: t`:

| File | Commands |
|---|---|
| `my-editing.el` | `my-duplicate-line`, `my-open-init-file` |
| `my-project.el` | `my-project-find-config`, `my-project-shell` |
| `my-treesit.el` | `my-enable-treesit` |
| `my-commands.el` | `my-command-palette` |
| `my-dev.el` | `my-dev-server` |
| `my-git.el` | `my-git-status` |
| `my-test.el` | `my-test` |

Each ends with `(provide 'name)`, which is what makes `(require 'my-editing)`
work once the directory is on `load-path`.

`my-treesit.el` is the only one that does something at load time: it defines
`my-enable-treesit` and then calls it, so the tree-sitter major modes are
remapped as a side effect of the `require` in `init.el`. It remaps `js-mode`,
`typescript-mode`, `json-mode`, `css-mode` and `html-mode` to their `-ts-`
variants, each guarded by `fboundp` so a missing grammar leaves the classic
mode alone.

`init.el` requires four of the seven. `my-commands`, `my-dev` and `my-git` are
reached through their autoloads instead.

### Autoloads

`.user-lisp-autoloads.el` is generated by Emacs's `loaddefs-generate` from the
`;;;###autoload` cookies above each `defun`. It holds one line per command:

```elisp
(autoload 'my-git-status "my-git" "Open Git status for the current project." t)
```

That is what lets `M-x my-git-status` work without `my-git.el` having been
loaded: Emacs knows the command exists and which file to load when it is
called. The trailing `t` marks it `interactive`, so it appears in `M-x`.

The file's own footer sets `no-byte-compile`, `no-update-autoloads` and
`no-native-compile` — it is generated output, and it says so in its first
line: *automatically extracted autoloads (do not edit)*.

Unlike the `.elc` files, this one **is** committed. It is a small text file,
it is what makes the commands discoverable on a fresh checkout, and
regenerating it requires knowing to.

### Compilation

Every `.el` in `user-lisp/` has a `.elc` beside it — byte-compiled output.
Emacs prefers a `.elc` over its `.el` when both are present and the `.elc` is
newer, so the compiled file is what actually loads.

:::warning[A stale `.elc` silently wins]
If a `.elc` is *newer* than its source, Emacs loads it and your edit does not
take effect. This is the single most confusing thing about a compiled
configuration: the file you are editing is not the file being run.

`M-x byte-recompile-directory` on `user-lisp/`, or deleting the `.elc`, is the
fix. Emacs does warn about a source newer than its compiled form, but the
warning is easy to miss in a `--daemon` start.
:::

None of the `.elc` files are committed — see below.

## What is not committed

`QDtb/.gitignore` has a long Emacs section, and everything in it is generated:

| Pattern | What it excludes |
|---|---|
| `*.elc`, `user-lisp/*.elc` | Byte-compiled output. Regenerated from the source, and **architecture- and version-specific** |
| `/eln-cache/`, `native-lisp/` | Native compilation output (Emacs 28+) — the same, more so |
| `/elpa/`, `elpa/`, `/straight/`, `/elpaca/` | Downloaded packages, from whichever package manager |
| `custom.el` | Written by Emacs's Customize interface |
| `gnupg/` | `package.el`'s signature keyring |
| `/auto-save-list/`, `auto-save-list/` | Recovery state |
| `\#*\#`, `.\#*` | Auto-saves and lock files |
| `/places`, `recentf`, `/url/`, `/var/`, `/etc/`, `/eshell/`, `/tramp`, `/games/` | Per-machine runtime state |

Two of these matter more than the rest.

**Compiled Lisp.** A `.elc` is tied to the Emacs version that produced it, and
an `.eln` to the architecture as well. Committing them means a checkout on
another machine loads bytecode built for an Emacs that is not there. They are
build output, and rebuilding them is one command.

**`elpa/`.** Downloaded packages are not your configuration; the *list* of
them is. `package-selected-packages` in `custom.el` would normally be that
list — except `custom.el` is ignored too, so the record lives in `init.el`'s
`(require 'atomic-chrome)`. With one package that is fine. With more, the
usual answer is to declare them explicitly, which
[the MELPA page](/docs/other/emacs-melpa#pinning-what-is-installed) covers.

The directories are still present on this machine — `elpa/` holds
`atomic-chrome-20230304.112` and `websocket-20260301.157`, and
`auto-save-list/` has three files — they are just not tracked.

## The rest of the directory

Six `.txt` files — `Vanilla.txt`, `Phone.txt`, `Spacemacs.txt`,
`Spacemacs_Backup.txt`, `Spacemacs_env_Backup.txt` — plus
`Emacs.code-workspace`. Notes and older configurations from before this one,
kept until they are either folded in or dropped. They are not loaded by
anything.
