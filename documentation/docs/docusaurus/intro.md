# Documentation

This section is about the site you are reading rather than about the
configuration it documents.

[**QDtb-doc**](https://github.com/natebass/QDtb-doc) is a separate repository
from [**QDtb**](https://github.com/natebass/QDtb). The configuration is
copied into `QDtb/` here, and the documentation is built around that copy — so
this repository contains both the source being described and the site
describing it.

## Layout

```text
QDtb-doc/
├── QDtb/                  a copy of the configuration repository
├── nvim-docusaurus/       the Docusaurus plugin that reads it
├── documentation/         the Docusaurus site
│   ├── docs/              the pages — mostly hand-written
│   │   └── reference/     generated, and gitignored
│   ├── blog/
│   ├── src/               components, pages, data, CSS
│   ├── scripts/           dump-theme-highlights.lua
│   ├── static/
│   ├── docusaurus.config.ts
│   └── sidebars.ts
├── .github/workflows/deploy.yml
├── package.json           the workspace root
└── pnpm-workspace.yaml
```

A pnpm workspace with two packages, `documentation` and `nvim-docusaurus`, and
a root `package.json` that forwards the common scripts to them.

## Keeping the copy in sync

`QDtb/` is kept up to date by copying from the main repository by hand. There
is no submodule and no subtree, so a change made in QDtb does not appear here
until it is copied across, and a change made here does not go back.

That is worth knowing when reading a page: what is documented is the copy in
`QDtb/`, at whatever commit it was last synced. `git log -- QDtb/` shows when
that was.

## What is generated and what is written

| Content | Source |
|---|---|
| `docs/reference/**` | Generated on every build from `QDtb/**/*.lua` |
| `src/data/theme-highlights.json` | Generated by hand, from a real Neovim |
| `src/data/keymaps.ts` | Written by hand, transcribed from `keymaps.lua` |
| Everything else in `docs/` | Written by hand |

The split is deliberate, and the rule behind it is: **generate what a machine
can read off the source, and write what it cannot.** A module's header comment
is in the file, so the reference generator takes it. Why `<leader>w` waits
300 ms before formatting is not in any file, so it is
[written down](/docs/neovim/keymaps#where-the-conflicts-are).

The two hand-generated data files —
[theme highlights](/docs/neovim/color-themes) and
[keymaps](/docs/neovim/keymaps#keeping-this-page-accurate) — are the middle
case: a machine *could* produce them, but only with Neovim present, which the
build machine does not have.
