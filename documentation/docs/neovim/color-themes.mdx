:::info[Where these colours come from]
Not from the hex values in the scheme files. `mini.hues` treats the background
and foreground written in each file as *reference* colours and adjusts them
when it builds the palette — `miniwinter` asks for `#cfd4e2` and Neovim renders
`#d8d4cd`.

So the previews above are dumped from a real Neovim by
[`documentation/scripts/dump-theme-highlights.lua`](https://github.com/natebass/QDtb-doc/blob/master/documentation/scripts/dump-theme-highlights.lua),
one scheme per process, for both values of `'background'`. The result is
committed at `documentation/src/data/theme-highlights.json` and regenerated by
hand when a scheme changes, because GitHub Actions has neither Neovim nor
mini.nvim to compute the palettes with.
:::

## The four seasons, and grey

Five of the seven are the same twenty lines with different numbers. Each one:

1. reads `vim.o.background` into `is_dark`;
2. picks a background and a foreground hex for each case;
3. hands them to `mini.hues` with a saturation and an accent.

```lua
local is_dark = vim.o.background == "dark"
local bg = is_dark and "#11262d" or "#dce4e8"
local fg = is_dark and "#cfd4e2" or "#2a2e39"

require("mini.hues").setup({
  background = bg,
  foreground = fg,
  saturation = is_dark and "lowmedium" or "mediumhigh",
  accent = "azure",
})

vim.g.colors_name = "miniwinter"
```

`mini.hues` generates the other several dozen highlight groups from those four
values. The comments in each file give the intent in OKLch — `miniwinter`'s
is `bg=15-3-225 and fg=85-2-270` — and note that the foreground hues are
"picked to maximize palette's bg colors visibility".

### The two patterns

There are two ways to drive `mini.hues`, and this set uses both:

| Pattern | Schemes | What it allows |
|---|---|---|
| `setup({ ... })` | `minisummer`, `miniwinter` | One call, done |
| `make_palette()` → tweak → `apply_palette()` | `miniautumn`, `minispring`, `minigrey` | Editing the palette before it is applied |

The second exists for one reason: the `accent = "bg"` schemes need the accent
to survive next to diff colours.

```lua
local p = hues.make_palette({ ..., accent = "bg" })
p.accent_bg = p.red_bg    -- miniautumn
hues.apply_palette(p)
```

`miniautumn` promotes red's background shade because `MiniDiffSignDelete` uses
red; `minispring` does the same with green, because `MiniDiffSignAdd` does.
Without it, the accent and the diff sign would sit at the same lightness and
the sign would disappear into the accent.

:::note[`setup()` leaves an autocommand behind]
`mini.hues.setup()` installs a `ColorScheme` autocommand that reapplies its own
configuration. Switching between `minisummer` or `miniwinter` and another
scheme in the same session can therefore leave the previous one's adjustments
in place. This is why the dump script runs one scheme per Neovim process, and
it is worth knowing if a scheme looks wrong after cycling through several with
`<leader>p`. `:restart` — bound to `<leader>d` and `<leader>F` — is the
reliable reset.
:::

### minigrey goes further

`minigrey` is the only one that edits individual colours rather than just the
accent:

```lua
local less_p = vim.deepcopy(p)
less_p.orange, less_p.orange_bg = fg, bg
less_p.blue, less_p.blue_bg = fg, bg
```

Orange and blue are erased — replaced by the plain foreground and background —
which is what produces the "less colours" feel. Nine `nvim_set_hl` calls then
put colour back exactly where it carries information:

- `DiagnosticInfo`, its underline and its floating variant, in azure;
- `MiniHipatternsTodo` as azure-on-background, bold;
- `MiniIconsBlue` in azure and `MiniIconsOrange` in yellow, since the originals
  were just erased;
- `@keyword.return` and `@markup.heading.1` in the accent, bold;
- `Delimiter` in `fg_edge2`, the faintest foreground shade.

The header explains the method: rather than picking a reference hue and chroma,
tweak achromatic greys at chosen lightness levels until the background and
accent read as azure and diff's cyan reads as cyan. Lightness is 15 + 85 for
dark and 90 + 20 for light, "picked by hand".

## `neovim_colors`

600 lines, and mostly a design document. It comes from the work on Neovim's own
default colour scheme and states its goals up front:

- **Neovim-branded** — a green-blue feel, with red reserved for severe and
  yellow for mild.
- **Accessible**, with contrast ratios written down as targets rather than
  hoped for: `Normal` at CR ≥ 7, and `Visual`, comment-on-`CursorLine`, diff
  groups and `Search` all at CR ≥ 4.5.
- **Minimal without `'termguicolors'`**, richer with it.
- Dark and light are the same two palettes exchanged, which is what keeps them
  in step.

Everything is computed in Oklch through `mini.colors`, from three sets of
hyperparameters:

| Hyperparameter | Value | Meaning |
|---|---|---|
| Lightness `l` | `{ 5, 10, 20, 35 }` | float background, `Normal`, `CursorLine`, `Visual`/`Comment` |
| Chroma `c` | `grey = 1`, `light = 10`, `dark = 15` | darker colours need more chroma to look different |
| Hue `h` | grey 270, red 25, yellow 90, green 150, cyan 195, blue 240, magenta 330 | grey 270 is a "cold" UI grey; change it to 90 for warm, 180 for neutral cyan |

The light palette is the dark one mirrored: `convert(100 - l[n], ...)`.

Two switches at the top control what happens when it is sourced:

```lua
local show_data_buffer = false   -- open a buffer with the computed palettes,
                                 -- their contrast ratios, 8-bit approximations
                                 -- and copy-pasteable highlight_group.c lines
local apply_colorscheme = true   -- actually set the colours
```

Turning `show_data_buffer` on is how the numbers in the table above were
checked. It requires
[mini.colors](https://github.com/echasnovski/mini.colors) to be installed,
which this configuration does not install — `mini.nvim` bundles `mini.colors`,
so the `require` resolves.

## `nordstone`

The odd one out, and the most conventional: 500 lines of explicit highlight
groups over a named palette. No computation, no `mini.hues`.

- The palette is Nord's sixteen — `nord0` through `nord15` — extended with
  in-between shades (`nord3_500`, `nord3_700`, `nord11_900`) and a separate
  neutral grey ramp from `neutral_900` to `neutral_400`.
- It publishes the palette as `vim.g.theme_colors`, so other configuration can
  read the colours it is rendering with. Nothing does today.
- `hl()` builds a `:highlight` command string and runs it, with `link` handled
  as a separate `highlight!` call.

Two behaviours to know about:

- **`Normal` has no background** (`bg = "NONE"`). The terminal or GUI shows
  through. In Neovide, that is the window background; the preview above
  substitutes a neutral dark surface and says so.
- **It ignores `'background'`.** There is one palette, and setting
  `background=light` changes nothing — which is why the dark/light toggle
  leaves this card alone.

It also opens with `highlight clear` and a `syntax reset`, which the other six
do not, so it is the only scheme that fully discards what came before it.

## Switching themes

| Key | What it opens |
|---|---|
| `<leader>p` | `MiniExtra.pickers.colorschemes` — live preview as you move |
| `<leader>D` | `Telescope colorscheme` |

Neither writes the choice down. Nothing in this configuration calls
`:colorscheme` at startup, so Neovim's default is what you get after a restart
— set `vim.cmd.colorscheme("...")` in `lua/config/init.lua` to change that.

`vague.nvim` and `vscode.nvim` are also installed, from
[`plugin/packages.lua`](/docs/neovim/plugins#two-calls-two-policies), and show
up in both pickers alongside the seven above.

## `colors/domscheme-main/`

Not a Neovim colour scheme, and not loaded by anything. It is a vendored copy
of [DomScheme](https://github.com/domsch1988/domscheme), a `mini.base16`
palette its author ported to the other applications they use. The directory
holds the terminal formats — `konsole_dark` and `konsole_light`,
`windows_terminal_dark`, `xresources_dark` and `xresources_light`, and
`base16_dark` and `base16_light` — plus a screenshot and a README.

It is kept here to keep the terminal's palette next to the editor's. The
[reference generator](/docs/reference) skips the whole directory, since none of
it is Lua this configuration runs.
